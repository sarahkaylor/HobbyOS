## Two engine bugs found and fixed

### 1. `DG_SleepMs` slept SECONDS, not milliseconds

`src/user/doom/doomgeneric_hobbyos.c` called `sleep((int)ms)`. HobbyOS libc's
`sleep()` is POSIX **seconds** (`src/user/libc.c:617`: `SYS_SLEEP(seconds*1000)`),
so the engine's per-tic `I_Sleep(1)` (`d_loop.c:784`) was a **one-second nap**:
DOOM ran at ~1 tic/s instead of 35. That is why the title screen looked frozen
and why one keypress appeared to change exactly one frame.

Measured before the fix (bundle `evidence/gb091-probe/20261101T232312Z`), intel,
F1 Apps-menu launch, DOOM.BIN found by name at slot 18:

```
MAD t08 -> t13 (5 s, no input) : 0.000015   (43 px changed = the taskbar clock)
MAD t13 -> t16 (3 ENTERs)      : 0.017502   (183 006 px)
MAD t16 -> t21 (5 s, no input) : 0.000053
```

The frame was static except one repaint per keypress — the 1-tic-per-key
signature. Fix: `usleep(ms * 1000u)`.

After the fix the engine follows its own timeline (title → attract demo at
~9.5 s) and animates between frames.

### 2. A lone ESC byte was dropped

The desktop forwards the Escape key as one `0x1B` byte (`keymap[1]`), not as a
CSI sequence; `kq_drain` treated every `0x1B` as the start of `ESC [ A/B/C/D`
and `continue`d, so `KEY_ESCAPE` could never reach the engine and DOOM's menu
was unreachable from the keyboard. Fix: push `KEY_ESCAPE (27)` when the next
byte is not `[`.

## Addendum (2026-11-02): ESC opens the DOOM menu — measured with a menuactive instrument

A second instrumented run (temporary `menuactive` row in `DG_DrawFrame`, reverted
before the commit; bundle `evidence/gb091-keys2/20261102T022145Z`) settles what a
key actually changes. Markers decode to `keys`, `gamestate`, `menuactive`:

```
s0_title   (7.9 s, before any key)  keys=0  gamestate=3  menu=0
s1_after_esc (8.8 s)                keys=2  gamestate=3  menu=1   MAD vs title = 0.405971
s2_after_ret1(9.5 s)                keys=4  gamestate=3  menu=1
s3_after_ret2(10.3 s)               keys=6  gamestate=3  menu=1
s4_idle    (11.9 s, no input)       keys=6  gamestate=3  menu=1   MAD vs s3   = 0.000033
```

So **ESC (the lone-0x1B fix) opens the menu**: `menuactive 0 -> 1` and 40.6 % of
the whole frame changes; with no further input the frame is then static
(0.000033 over 1.5 s).  The frame `menu_after_esc.png` is the menu.

The window is narrow: the attract demo starts at ~8 s and ignores input, so ESC
must land on the title page (a second run with ESC at 7.8 s did not open it,
MAD 0.010).  `ENTER` in the menu changes the frame slightly (0.017, 0.014) but
leaves `menuactive=1`, `gamestate=3` — **starting a game is still not
demonstrated**; that remains the one unmet DoD clause.

## Playthrough (2026-11-02): the menu sequence starts a game, and a key turns the view

The earlier gap is closed. On the title page the full menu path is
**ESC (main menu) -> ENTER (episode select) -> ENTER (skill) -> ENTER (start)**;
DOOM (shareware/Freedoom, non-commercial) inserts the episode screen, which is
why the two-ENTER sequence used earlier stopped in a menu. Clean run (no
instrument), intel, F1 Apps-menu launch, keys at 7.6-7.9 s after launch:

```
k_game  (9.4 s, after esc,ret,ret,ret)  keys=4  gamestate=0  menu=0   [instrumented run]
k_idle  (11.1 s, no input)              -> 178 188 px changed (bbox starts y=284)
4 x right, then
k_turn  (13.0 s)                        -> 702 592 px changed (bbox spans the viewport)
```

MAD: idle pair **0.017831**, after four `right` presses **0.042642** (2.4x the
idle baseline), and the change bbox grows from the lower part of the view
(animated surfaces while the player stands still) to the whole viewport
(the camera turning). The final frame is a first-person level with the status
bar: AMMO 50, HEALTH 100.

The same sequence is in `tools/t5/replays/doom.jsonl` and reproduces through
the replay runner, which now launches the requested title **by name** from the
`[MENU]` dump instead of walking a fixed slot count:

```
$ python3 tools/t5/replay.py --game DOOM.BIN --replay tools/t5/replays/doom.jsonl \
      --arch intel --settle 5.0
[replay] DOOM.BIN slot: found by name = 18
[replay] replaying 8 in-game events
[replay] screendump after replay: evidence/replay/DOOM/20261102T030200Z/replay_end.ppm
```

That run's serial carries `[LAUNCH] DOOM.BIN` / `[ARRIVED] DOOM.BIN rc>0`, and
`replay_end.ppm` is the level frame (`replay_end.png` here).
