GB-240 — bracket the idle-stuck detector's proc_lock section
============================================================

Head: 8bdd2fefc484aa5e5627a3acf5fa3244b0f1c7f9 (origin/main) + the GB-240 commit.
Worktree: /home/sarah/Documents/GitHub/HobbyOS/.worktrees/gb240
SW-VM: swarm-farm-3 (verifier, debug reserve — gaming.md §5.1).

The card's premise
------------------
GB-232's disassembly attributed the imbalanced `[PROCLOCK-HOLD]` acquire
(`owner_site3=0x7007BC9D`) to the idle-stuck detector's `proc_lock` section at
process.c:4782. GB-240 asked for a per-CPU bracket of that section:
det_entry_ms on acquire, det_exit_ms on the release, det_stage at the branches
(1 slot scan, 2 dispose, 3 group_teardown, 4 release), printed on the
[PROCLOCK-HOLD]/[LOCKDIAG] row for the owner CPU.

What this branch adds
---------------------
- src/include/lock.h: proclock_hold_t gains det_entry_ms/det_exit_ms/det_stage;
  proclock_det_note(op, stage) is declared (op 1 entry, 2 stage, 3 exit).
- src/kernel/arch/x64/locks.c: proclock_det_note() writes the per-CPU stamp.
- src/kernel/arch/arm/locks.c: no-op stub (the shared process.c call site must
  still compile on ARM; ARM has no plh[] table).
- src/kernel/process.c:
  * after the detector's `spinlock_acquire_irqsave(&proc_lock)` (4782):
    proclock_det_note(1, 1);
  * stage 2 when a dispose slot is selected; stage 4 immediately at the
    release; exit stamp after the release returns; stage 3 before group_teardown;
  * [PROCLOCK-HOLD] prints det_entry/det_exit/det_stage for that CPU;
  * [LOCKDIAG] prints the OWNER CPU's det_entry/det_exit/det_stage.
  Existing scheduling behaviour is unchanged (observation only).

The wave wedged (halted=0, 33 programs) with 87 [PROCLOCK-HOLD] rows, 29
[LOCKDIAG] rows and 174 [IDLESTUCK] lines, so the detector stamps printed.

RESULT: the card's premise is FALSIFIED — every imbalanced row carries a
completed detector pair, and the unpaired acquire is the [IDLESTUCK] dump's
OWN proc_lock acquire, not the detector section.

Address resolution (llvm-addr2line on this build's hobbyos.elf):
```
0x7007BCDD -> start_scheduler process.c:5089   (the [IDLESTUCK] dump's
                                                `uint64_t dflags =
                                                 spinlock_acquire_irqsave(&proc_lock);`)
0x7007B4B5 -> start_scheduler process.c:4782   (the detector's acquire)
0x7007BB82 -> start_scheduler process.c:5022   (the detector's release)
```
The disassembly confirms the shape: at 0x7007BCC9-0x7007BCDD the dump prints
" rounds=" / " t=" / timer_get_ms then acquires 0x746E5088 (proc_lock); at
0x7007B4AB-0x7007B4C3 the detector acquires the same lock and immediately calls
proclock_det_note(1,1). The card's older `0x7007BC9D` is the same dump acquire
in the pre-instrument binary (the GB-240 additions shift it to 0x7007BCDD).

CPU 5's last detector pass completed at 310947 (last=release). CPU 7's last
detector pass completed at 310945 (det_entry=det_exit); at 310947 it acquired
proc_lock for the [IDLESTUCK] dump itself — that is the `acq=rel+1` row. The
[LOCKDIAG] rows then show the other CPUs waiting on the dump's lock
(wait_pc=spinlock_acquire_irqsave), not on a detector section.

Decision per the card
---------------------
The falsifier says: "if every imbalanced row shows a completed entry/exit pair,
this card's premise dies — return with the record and the next split, do not
guess." That is what the record shows (11/11 completed, 0 with det_exit=0), so
GB-240 returns with the record rather than a fix.

Next split (for the Coordinator; not minted here)
-------------------------------------------------
1. The [IDLESTUCK] dump holds proc_lock while it prints 87 [PROCLOCK-HOLD] rows
   over the UART; its own acquire is definitionally `acq=rel+1` in that dump.
   Either mark/skip the dumper's own row (`dump_self=1`) or snapshot the table
   under the lock and release before printing, so the row cannot be mistaken
   for a strand.
2. The real owner signal in this wave is the LOCKDIAG owner while the dump
   prints: `owner_cpu=7 owner_pid=-1 owner_wd_rip=0x1000005C84 owner_wd_pid=5`
   — a user VA on pid 5, i.e. the owner CPU was in user space while the dump
   held the lock. That, not the detector section, is the next candidate.
3. GB-232's attribution of the same site to the detector (4782) is not
   supported by this build: the unpaired acquire resolves to 5089.
