## Missions

### 1. ARM secondary cores under QEMU TCG (PSCI)
- Measured earlier (survived reap #2): `-smp 2` powers on core 1 — "System halt
  from CPU 1" proves it boots + schedules. `-smp 8` fails cores 2–7 with
  `PSCI error -2` (PSCI_CPU_ON refuses).
- Verdict: **still single-core in practice for the desktop/browser**; no
  working >2-vCPU config found. The config diff (wave runner `-cpu cortex-a53`
  `-smp N` vs desktop's `-smp 1`) and the kernel PSCI conduit (arm64 hvc
  PSCI v0.2) remain the suspects — left as next steps, no kernel change landed
  (would need the standard gates; not done this wave).

### 2. Serial-write cost + quiet mode
- **SRLCOST.BIN** harness landed (`src/user/serial_cost.c` + Makefile wiring +
  `.arch-stamp`), commit `f9518fc`.
- Numbers: **≈2.37 µs/byte `-smp 1`, ≈2.44 µs/byte `-smp 2`** (MTTCG, +3%
  contention). A 1000-char line ≈ 2.4 ms; the browser's 80-char [WIN] spam
  lines ≈ 190 µs each. On a page with thousands of repaint lines that is
  seconds per run.
- Proposal: **`CONSOLE_QUIET=1`-style knob** (no defaults changed) that the
  runner sets in-guest; suppresses only the per-frame [WIN] spam, keeps
  crash/watchdog lines on. Not implemented in a browser lane — parked for a
  fork/browser lane to adopt.

### 3. x64 clock/launch sanity (KVM)
- **X2 TSC fix ACTIVE**: every boot probe (8 across PX run3, M1 run 801, and
  my 4 probes this session) prints
  `TSC rate: 2596xxx ticks/ms (PIT-counter calibrated)` = host TSC (2.596 GHz).
  The PIT-counter calibration (commit `2f48639`) is the active path.
- **Guest monotonic tracks host wall 1:1 under KVM**: on both wedged probes the
  guest `IDLESTUCK t=` (kernel monotonic ms) vs my host-wall stamp:
  `74332/74551 = 0.997` and `92528/92717 = 0.998`.
- **The PX "guest 11.7 s vs wall 47.8 s" is an anchor artifact, not a clock
  defect**: `[WIN] load-ok ms=` is `MonotonicTime::now() - m_start` with
  `m_start` set once at window-driver construction (WK5WindowDriver.cpp:657) —
  a per-session elapsed timer, not a boot-anchored wall clock.
- Launch composition (PX run3, only clean full load on record): kernel boot
  3.3 s → Mode DESKTOP → [WIN] BOOT 10.2 s → **101 MB webproc image prefault
  (IMGPRF) = 30.06 s guest / 30.42 s host** → HOME frame 40.6 s. The "10 s
  launch" is dominated by the image prefault, not the clock.
- **New blocker found (bonus)**: fresh boots of the pinned x64 disk wedge at
  the DESKTOP menu in **4/4 probes** (console silent, watchdog, cores idle at
  `0x7002A296`, no [WIN] BOOT). M1's live 801 on the same disk got HOME but
  then wedged on the cnn.com fetch. Same stuck-idle family the X2 lane fought —
  worth a P3 lane. It blocked a clean end-to-end load-ok in my probes.
