Subject: [PATCH 1/2] kstack: pin a kernel task's stack while schedule() is
 still on it; detector + probe (no fix yet)

A kernel task runs in ring 0 on its own stack, so its interrupts (yield,
the 100 Hz broadcast 0x81, a blk-cache wait) run schedule() on that stack.
schedule() saves the task, makes it READY, claims the next slot, drops
proc_lock and only then runs the switch tail on the old stack until
enter_user_space leaves it.  Nothing stops another CPU from resuming the
task in that window, onto the frames the first CPU is still using.

This commit only measures it: cpu_locals.kstack_pin (gs:[56]) names the
kernel task whose stack this CPU is still on (set under proc_lock by the
CPU that gives the task up, cleared by enter_user_space before the iretq
and by start_scheduler after a longjmp), and both pick sites report a
resume of a pinned task as [KSTACK-SHARE].  Test kernels get a stress
(kernel tasks yielding in a loop, LX_HB_TEST_KSTACK) and the kstack probe
with its console checker, which fail on any share, fault or lock-strand row.

+/* C6-p7b: a kernel task's stack outlives its claim.
+ *
+ * A kernel task runs in ring 0 on its own stack (process_create_kernel), so
+ * an interrupt it takes -- the int 0x81 of a yield, the 100 Hz broadcast
+ * 0x81, the blk-cache wait's yield -- pushes its frame onto THAT stack and
+ * schedule() runs there.  schedule() saves the task, makes it READY (or
+ * leaves it parked), claims the next slot and drops proc_lock, and only then
+ * runs the switch tail -- resume diagnostics, vm_touch, the next thread's
+ * signal delivery, enter_user_space's frame check -- still on the task's
+ * stack, until enter_user_space moves RSP or iretqs.  The claim
+ * (cpu_current_pids) is already gone, so another CPU may pick the task in
+ * that window and resume it at its saved RSP: the resume copies its frame to
+ * [rsp-320, rsp) and the task then runs below rsp -- over the frames this
+ * CPU is still executing.  Measured (integ9 Gate P5, fullscreen row): CPU 7
+ * (now "pid 9", icewm) and CPU 6 (pid 270, the image-prefetch task) both in
+ * spin_acquire_raw(&proc_lock) on ONE stack (trap frame 0xFFFF800023FFD7F0
+ * on both), CPU 7 #PF at the __builtin_return_address(1) walk (saved RBP

+ * src/user/linux_probe_kstack.c — a kernel task's stack must not be resumed
+ * on one CPU while another CPU is still running on it (C6-p7b).
+ *
+ * The integ9 Gate P5 fault: the image-prefetch kernel task, preempted on its
+ * own stack, was picked by CPU 6 while CPU 7 was still in schedule()'s switch
+ * tail on that stack (it had claimed icewm next); both CPUs faulted inside
+ * spin_acquire_raw(&proc_lock) with one trap-frame address between them.
+ *
+ * ORDINARY musl Linux program.  Rows "[LP] ...", last "[LP] done rc=<fails>".
+ * It needs a TEST kernel (MODE=test, i.e. tools/gate/t3_linux_probe.sh): the
+ * stress lives in the kernel and is reached through the test-only compat
+ * syscall 0x4B5354 ('KST', trap.c), which a release kernel answers -ENOSYS.

+import sys
+
+BAD = [
+    ("kstack-share", re.compile(r"\[KSTACK-SHARE\]")),
+    ("kernel-fault", re.compile(r"FATAL: Exception in Kernel Mode|FATAL kernel-mode fault")),

+    if not starts:
+        fails.append("no [KSTACK-ST] start row (the stress never ran)")
