# C3-fat: P9-8 (fat_lock wedge) root cause, reproducer and A/B.  Host: strix (Zen 5, KVM, -smp 8 -m 12G guests)
# Branch cp-fat: first from integ9 adb81ee4 (all A/B below up to "integ10" ran there), final on integ10 49e83499.  Probe: src/user/linux_probe_fatren.c via tools/gate/t3_linux_probe.sh (FAT-only boot,
# 30 s of traffic); QMP register/stack sampler: T3_MONITOR=1 + a side script dumping `info registers` + 48 stack words per vCPU
# on the first [YLOCK-WEDGE].

## Verdict
P9-8 is NOT a FAT lock-order bug and NOT the kernel-stack sharing race.  It is a lost wakeup in the NVMe single-in-flight
device token (virtio_blk.c blk_token_acquire), made fatal by the x86 tick topology:

 1. A FAT directory / FAT-sector / page-in operation holds fat_lock (or fat_wr_lock) across device I/O, so it waits for the
    device token while holding the lock.  The ext2 side does the same under ext2_lock (the token is shared by namespace 1,
    FAT, and namespace 2, the cp/ext2 data disk).
 2. The token wait was `safe_wfi()` ("sti; hlt") in a loop; it re-checks only when SOME interrupt arrives, and
    blk_token_release() woke nobody.
 3. An AP has no periodic interrupt of its own (timer.c: the AP LVT is not armed; C1-k6's 0x84 one-shot fires only for a
    covered park deadline).  Its only periodic wake is CPU 0's PIT tick, which broadcasts 0x81.
 4. CPU 0 stops broadcasting whenever it runs with IF=0, and syscall entry masks IF (SFMASK 0x47700), so a CPU-0 thread
    spinning in ylock_acquire on the lock the halted waiter holds spins with interrupts OFF.
 => the token is released, the halted holder is never woken, nothing moves: [YLOCK-OWNER] ost=3 (RUNNING) on a CPU in HLT,
    no [BLKQ] row, token free.  Same shape as C3-ext2w's ext2_lock "lost holder" (its F5 dump: CPU#0 RFL=0x97, i.e. IF=0,
    spinning on ext2_lock; the holder's CPU#3 in safe_wfi).

P9-8's own row `osys=23` is the holder's LAST syscall as a LINUX number: 23 = select, not SYS_RENAME (the play lane's
report says rename).  IceWM's last console row was a fontconfig rename, but at the wedge it was inside select -- most likely
a page fault on a FAT-backed mapping taking fat_lock in the page-in path (the sampler's second spinner was under
fat16_read_direct_locked).  Not proven; the mechanism is the same either way.

## ext2 inversion found on the way (ipiext v1, fixed for the token wait; the general hazard is C1-k6's)
[YLOCK-OWNER] ext2_lock pid=1 cpu=0 pcb_live=1 ost=2 osys=-1      <- the ext2 flusher (kernel task), READY, not running
The first IPI cut also halted KERNEL tasks in the token wait.  0x81 on a kernel task is a reschedule, so the wake
preempted the flusher while it held ext2_lock; every other CPU was in an unpreemptible syscall spinning with IF=0, so
nobody ran it again.  The same run also lost a user waiter's wake (two CPUs halted in blk_token_acquire, token free): a
preempted kernel task resumed on another CPU and cleared a sleeper bit that was no longer its own.  Kernel tasks now
poll (no halt, no bit).  The tick can still preempt a kernel task holding a ylock, exactly as before this branch: that
part is pre-existing and listed for C1-k6 in wfi-sites-for-c1k6.txt.  (Final code: kernel tasks halt in plain
safe_wfi(), bounded by 9d47b051, and never register for the release wake.)

## The two FAT bugs the reproducer found on fontconfig's exact path (fixed in 59e26be9)
 - rename(".NEW" -> final) compared 8.3 names to decide "destination is a different entry"; all fontconfig cache names
   truncate to the same 8.3 form, so the old final was never unlinked and kept answering lookups (V1: final holds
   generation 1 after 99 updates) and a stale entry was added per update.
 - a VFAT run that did not fit in the sector holding the 0x00 end marker was placed behind that marker (next/new
   cluster), invisible to every lookup: create OK, then rename TMP->NEW ENOENT at generation ~100.
Both reproduce in-kernel too: test_fat16_rename_fontconfig_cache (unit tier).
