# LIBC.SO — lane C build evidence

Produced by `tools/build_libs.sh` (docs/shared-libs.md §4 lane C).  The full,
machine-generated dumps live next to the artifacts in
`obj/<arch>/libc.so.evidence.txt` and `obj/<arch>/libc.so.map` (both
gitignored, regenerated by `tools/build_libs.sh all`); this file is the durable
summary so the numbers survive a clean checkout.

## Reproduce

```sh
make ARCH=arm   obj/arm/libc.a      # archive baseline for the size column
make ARCH=intel obj/intel/libc.a
tools/build_libs.sh all            # obj/<arch>/libc.so + evidence
tools/build_libs.sh link_probe all # link a throwaway program against it
tools/elf-dyn/gen_so_fixtures.sh   # fixtures for lane D (+ --check to diff)
```

## Linkable, not just loadable

`tools/build_libs.sh link_probe <arch>` builds the §5 pilot shape — a tiny
ET_DYN program that imports `strlen`, `malloc`, `free`, `strcmp` — and links it
against `obj/<arch>/libc.so`:

```
$ ld.lld -pie --no-dynamic-linker -e _start -z relro -z now -z defs \
          -z noexecstack --hash-style=both -o APP.ELF probe.o obj/<arch>/libc.so

arm:   Type DYN (Position-Independent Executable file), Entry 0x10320,
       NEEDED LIBC.SO, imports {malloc, strlen, strcmp, free}
intel: Type DYN (Position-Independent Executable file), Entry 0x1380,
       NEEDED LIBC.SO, imports {malloc, strlen, strcmp, free}
```

So LIBC.SO's `.dynsym` is a usable link input (types/sizes/bindings are right
on every export), `DT_SONAME LIBC.SO` propagates into the consumer's
`DT_NEEDED`, and the result has the ET_DYN + real-entry shape the kernel and
interpreter expect.

## Reading of the numbers

* `.dynsym` holds exactly the symbols frozen in `src/libc/libc.map` plus the
  null entry; the map is the union of both arches' `libc.a` globals (637), so
  each arch exports the subset it actually defines (637 arm / 613 intel — the
  difference is the aarch64-only binary128 compiler-rt builtins).
* No `TEXTREL`, and the link runs with `-z text`, so a future TU that would
  need a text relocation fails the *link* instead of shipping a
  self-modifying DSO.
* Every `R_*_TPREL64`/`R_X86_64_TPOFF64` relocation is a GOT slot the loader
  must fill, and the two architectures want different arithmetic (their TLS
  ABIs are variant I and variant II).  `addend` already carries the symbol's
  offset inside libc.so's TLS block (lld resolved the symbol and left
  `sym == 0`); `DF_STATIC_TLS` says the module expects a slot in the per-thread
  static block.  With `off` = the module's byte offset inside that block and
  `BLOCK` = the block's total (aligned) size:
    aarch64 (variant I):  slot = off + addend            (addressed as TP+slot)
    x86_64  (variant II): slot = off + addend - BLOCK    (addressed as TP+slot,
                                                          i.e. below the TP)
  tools/elf-dyn/golden/<arch>/LIBUSE.SO.dyn.txt pins the same shape on a
  fixture that is easy to inspect (one .tdata and one .tbss variable).
* `R_X86_64_64` / `R_AARCH64_ABS64` is `__dso_handle` (cxxrt.cpp defines it as
  a pointer to itself); it is a normal absolute relocation in a writable
  section.
* All four `PT_LOAD` segments have `p_vaddr == p_offset`, so an interpreter
  that maps the whole file at a 16 MiB `USER_LIB` slot base with one
  `SYS_MMAP` gets every segment at its `p_vaddr` without offset fixups.

## Notes handed to the coordinator / lane D

* **No source change was required for PIC.** Not one file under
  `src/libc/src/**`, `src/user/**` or the Makefile was touched: every TU
  compiles clean with `-fPIC -ftls-model=initial-exec`, and the TLS bootstrap
  in `src/user/libc.c` / `src/libc/src/pthread.c` links unchanged because
  `src/libc/linker_so.ld` defines `__tls_start`, `__tls_data_end`, `__tls_end`,
  `__tls_align` and `__tls_meta_align` with the same semantics as
  `src/user/linker.ld`.
* `DT_INIT_ARRAY`/`DT_FINI_ARRAY` are present with **size 0** (no constructor
  in the libc objects).  A loader that walks them must treat size 0 as "none".
* `libc.so` has **no `DT_NEEDED`** — it is a leaf module.  Only the program's
  own `DT_NEEDED` chain names `LIBC.SO`.
* Staging: copy `obj/<arch>/libc.so` to the disk root as `LIBC.SO` (8.3).  The
  `DT_SONAME` is already `LIBC.SO`, so `DT_NEEDED LIBC.SO` resolves.
* `_end` is defined inside libc.so (end of its `.bss`).  `src/user/malloc.c`
  only uses `_end >= USER_VA_BASE` to pick the v2 heap slot, and a DSO mapped
  in `USER_LIB` (≥ `USER_VA_BASE`) takes the same branch the flat image did, so
  malloc behaves identically.  If a later phase wants `_end` to mean "end of
  process image", the interpreter must supply it and the map must stop
  localising the DSO's copy.
* `ho_tls_setup_initial()` / `pthread.c`'s TLS block builder remain exported and
  keep working against libc.so's own TLS image; once lane D installs the static
  block for the process they are dead code for dynamically linked programs but
  still serve statically linked ones.
* x86_64 libc.so is built with `-mcmodel=large` (user images live at 64 GiB),
  which is why its imports are `GLOB_DAT`-heavy (functions are reached through
  the GOT) and why its sections carry `SHF_X86_64_LARGE`.  Section flags are
  irrelevant to the loader — only `PT_LOAD` `p_flags` matter.
